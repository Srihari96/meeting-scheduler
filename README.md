# Meetly — One-on-One Meeting Scheduler

Meetly is a calendar-based one-on-one meeting scheduler built with Django, Django REST Framework, PostgreSQL and LiveKit.

Users can register, configure their preferred timezone and minimum scheduling notice, schedule meetings with other users, detect conflicting meetings, view scheduled/cancelled/completed meetings, and join browser-based video calls.

This project is currently an MVP intended for local development, demonstration and functional testing.

## Features

### User management

* User registration
* Session-based login and logout
* Django admin support
* Preferred timezone selection
* Configurable minimum scheduling notice
* Password hashing through Django’s authentication system

### Meeting scheduling

* One organizer and one invitee per meeting
* Future meeting scheduling
* Start and end time validation
* Invitee-based minimum-notice validation
* Conflict detection for both participants
* Back-to-back meetings are allowed
* Meeting cancellation by the organizer
* Scheduled, cancelled and completed meeting states
* Meetings ordered by start time in descending order

### Timezone handling

* Users select a preferred IANA timezone
* Meeting input is interpreted using the selected input timezone
* Meeting timestamps are converted to UTC before persistence
* PostgreSQL stores timezone-aware timestamps
* API responses include times localized to the authenticated user
* The dashboard displays meetings in the user’s preferred timezone

### Video calling

* One LiveKit room per meeting
* Short-lived participant tokens generated by Django
* Only the organizer and invitee can request a token
* Tokens are scoped to one specific room
* Configurable early-join window
* Cancelled and completed meetings cannot be joined
* Camera and microphone controls
* Mute and unmute
* Camera on and off
* Participant connection states
* Waiting-for-participant message
* Leave-call functionality

### User interface

* Responsive Django-template interface
* Registration page
* Login page
* Meeting dashboard
* Scheduled, cancelled and completed filters
* Schedule-meeting dialog
* Join-call button

* API-backed frontend operations using browser `fetch()`

## Data model

### User

The project uses a custom Django user model.

Additional fields:

| Field                    | Description                                                             |
| ------------------------ | ----------------------------------------------------------------------- |
| `preferred_timezone`     | IANA timezone used for meeting display and default input                |
| `minimum_notice_minutes` | Minimum notice another user must provide when scheduling with this user |

The minimum-notice preference applies only when the user is the invitee.

For example:

* Alice has a 30-minute minimum notice.
* Bob schedules a meeting with Alice.
* The meeting must start at least 30 minutes from the current time.
* If Alice schedules a meeting with Bob, Alice’s own notice setting does not restrict her.

### Meeting

| Field           | Description                                  |
| --------------- | -------------------------------------------- |
| `title`         | Meeting title                                |
| `description`   | Optional meeting description                 |
| `organizer`     | User who created the meeting                 |
| `invitee`       | User invited to the meeting                  |
| `starts_at`     | Timezone-aware start timestamp               |
| `ends_at`       | Timezone-aware end timestamp                 |
| `status`        | Persisted status: `scheduled` or `cancelled` |
| `video_room_id` | Unique LiveKit room UUID                     |
| `created_at`    | Creation timestamp                           |
| `updated_at`    | Last modification timestamp                  |

### BusySlot

A `BusySlot` is created for each meeting participant.

Every meeting creates two busy slots:

* One for the organizer
* One for the invitee

Each busy slot contains:

* Meeting
* User
* PostgreSQL timestamp range
* Active state

PostgreSQL uses an exclusion constraint to prevent overlapping active ranges for the same user.

This provides database-level conflict protection, including protection against concurrent requests that pass application-level checks at nearly the same time.

## Meeting interval behavior

Meeting intervals use half-open ranges:

```text
[start_time, end_time)
```

The start time is included and the end time is excluded.

Therefore, back-to-back meetings are allowed:

```text
Meeting A: 10:00–10:30
Meeting B: 10:30–11:00
```

But overlapping meetings are rejected:

```text
Meeting A: 10:00–10:30
Meeting B: 10:15–10:45
```

## Meeting statuses

The database persists two statuses:

```text
scheduled
cancelled
```

`completed` is computed dynamically by the API.

The effective status follows this logic:

```text
If persisted status is cancelled:
    status = cancelled
Else if ends_at <= current time:
    status = completed
Else:
    status = scheduled
```

Completed is not stored because a meeting naturally becomes completed as time passes. Persisting it would require a scheduled background process to update meeting rows.

Cancelled takes precedence over completed.

## Conflict detection

A meeting cannot be created if either participant has another active meeting whose interval overlaps the requested interval.

Conflict protection is implemented using a PostgreSQL `ExclusionConstraint`.

The `btree_gist` PostgreSQL extension is required because the constraint combines:

* Equality comparison on `user_id`
* Range-overlap comparison on `time_range`

The migration enables the extension using:

```python
from django.contrib.postgres.operations import BtreeGistExtension
```

The extension operation must execute before the exclusion constraint is created.

## Timezone design

Django is configured with:

```python
TIME_ZONE = "UTC"
USE_TZ = True
```

Users select from a small MVP timezone list:

* UTC
* India — Asia/Kolkata
* US Eastern — America/New_York
* UK — Europe/London
* Australia — Australia/Sydney

The model stores the timezone as an IANA timezone name.

Example meeting request:

```json
{
  "start_time_local": "2026-09-10T14:30:00",
  "end_time_local": "2026-09-10T15:00:00",
  "input_timezone": "Asia/Kolkata"
}
```

The API:

1. Interprets the input as Asia/Kolkata.
2. Converts it into UTC.
3. Stores the timezone-aware timestamp in PostgreSQL.
4. Converts it into the requesting user’s preferred timezone when serializing the meeting.

All comparisons—conflict detection, completed status and join-window checks—operate on timezone-aware absolute timestamps.

## Local installation

### 1. Enter the project

```bash
cd meeting_scheduler_starter
```

### 2. Create a virtual environment

```bash
python3 -m venv .venv
```

Activate it:

```bash
source .venv/bin/activate
```

### 3. Install dependencies

```bash
pip install -r requirements.txt
```

The requirements should include:

```text
Django
djangorestframework
psycopg[binary]
python-dotenv
livekit-api
```

### 4. Create the PostgreSQL database

```bash
createdb meeting_scheduler
```

Alternatively:

```bash
psql postgres
```

Then:

```sql
CREATE DATABASE meeting_scheduler;
```

Exit:

```sql
\q
```

### 5. Configure environment variables

Copy the example file:

```bash
cp .env.example .env
```

Example local `.env`:

```env
DJANGO_SECRET_KEY=local-development-secret-key
DJANGO_DEBUG=True

POSTGRES_DB=meeting_scheduler
POSTGRES_USER=postgres
POSTGRES_PASSWORD=postgres
POSTGRES_HOST=localhost
POSTGRES_PORT=5432

LIVEKIT_URL=ws://127.0.0.1:7880
LIVEKIT_API_KEY=devkey
LIVEKIT_API_SECRET=secret

VIDEO_JOIN_EARLY_MINUTES=10
```

For easier manual testing, the join window can temporarily be increased:

```env
VIDEO_JOIN_EARLY_MINUTES=1440
```

This permits users to join up to 24 hours before the scheduled start time.

Do not commit `.env`.

### 6. Apply migrations

```bash
python manage.py migrate
```

The meetings migration automatically enables the PostgreSQL `btree_gist` extension.

If the database user does not have permission to enable extensions, enable it manually using an appropriately privileged PostgreSQL user:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;
```

Then run migrations again:

```bash
python manage.py migrate
```

### 7. Create an administrator

```bash
python manage.py createsuperuser
```

### 8. Start Django

```bash
python manage.py runserver
```

The application is available at:

```text
http://127.0.0.1:8000/
```

## Cancel a meeting

Only the organizer can cancel a meeting.

```bash
curl -X POST \
  http://127.0.0.1:8000/api/meetings/1/cancel/ \
  -u alice:password123
```

Cancelling a meeting marks its busy slots as inactive. The time interval then becomes available for new meetings.

## Generate a LiveKit participant token

The user must be the organizer or invitee.

```bash
curl -X POST \
  http://127.0.0.1:8000/api/meetings/1/video-token/ \
  -u alice:password123
```

Example response:

```json
{
  "server_url": "ws://127.0.0.1:7880",
  "participant_token": "eyJhbGciOiJIUzI1NiIs...",
  "room_name": "21c9080a-483a-4d69-bd10-970783dc4081"
}
```

The endpoint rejects the request if:

* The authenticated user is not a participant
* The meeting is cancelled
* The meeting has ended
* The configured join window has not opened

The LiveKit API secret is used only by Django and is never exposed directly to browser JavaScript.

## Video-call workflow

1. User opens the meeting dashboard.
2. The Join call button becomes available during the join window.
3. User opens `/meetings/{id}/call/`.
4. The browser requests a token from Django.
5. Django verifies the authenticated user and meeting state.
6. Django generates a short-lived LiveKit JWT.
7. The browser connects to LiveKit.
8. The browser requests camera and microphone permission.
9. Local tracks are published.
10. Remote tracks are automatically subscribed and rendered.
11. Leaving disconnects the participant from the room.

## Testing a two-user call

1. Start PostgreSQL.
2. Start LiveKit Server.
3. Start Django.
4. Open the application in a standard browser window.
5. Log in as the organizer.
6. Open an incognito window or a second browser.
7. Log in as the invitee.
8. Open the same meeting in both sessions.
9. Join the call from both.
10. Allow camera and microphone access.

Use headphones when testing two sessions on the same computer to prevent audio feedback.

Verify:

* Both users can see each other
* Both users can hear each other
* Mute works independently
* Camera-off works independently
* Participant media states update
* Waiting state appears when only one participant is connected
* Leaving removes the participant tile
* Unrelated users cannot access the meeting room

## Security decisions

### API secrets

The following values must not be committed:

* Django secret key
* PostgreSQL password
* LiveKit API secret

They must be stored in `.env` locally and as environment variables when hosted.

### LiveKit room names

Meeting rooms use generated UUIDs instead of:

* Usernames
* Email addresses
* Meeting titles
* Other personally identifiable information

### Meeting visibility

The meeting API queryset only contains meetings where the authenticated user is either:

* Organizer
* Invitee

An unrelated user receives `404` for meeting details and video tokens.

### Video tokens

LiveKit tokens are:

* Generated by Django
* Short-lived
* Scoped to one room
* Restricted to authenticated meeting participants
* Granted publish and subscribe access
